# Monitoring and Logging Specification

## Purpose
This document defines the full observability stack for Grahvani -- structured logging format, application performance monitoring, AI-specific observability, alerting thresholds, and runbook references. It provides the foundation for the on-call engineer to understand the system's health at any moment.

## Scope
Covers the FastAPI backend, Dramatiq worker, and Flutter client crash reporting.

---

## 1. Observability Stack

| Layer | Tool | Purpose |
| :--- | :--- | :--- |
| **Structured Logging** | Python `structlog` + CloudWatch Logs | Per-request JSON logs with correlation IDs |
| **Metrics and APM** | Amazon CloudWatch Metrics | HTTP latency, error rates, CPU, RAM, queue depth |
| **Error Tracking** | Sentry SDK | Exception stack traces with context for both backend and Flutter |
| **AI Observability** | Langfuse | LLM trace logs, groundedness scores, token counts, latency per request |
| **Uptime Monitoring** | CloudWatch Synthetics Canary | Periodic `GET /api/v1/health` probes every 60 seconds |
| **Dashboard** | CloudWatch Dashboard | Single-pane-of-glass: SLO adherence, error budget burn |

## 2. Structured Log Format

All backend logs are emitted as structured JSON to CloudWatch Logs, making them queryable via CloudWatch Insights:

```json
{
  "timestamp": "2026-08-04T14:00:00.412Z",
  "level": "INFO",
  "request_id": "req-8a4f9b12",
  "user_id": "uuid-omitted-for-pii",
  "module": "interpretation",
  "action": "rag_search_complete",
  "duration_ms": 42,
  "chunks_retrieved": 4,
  "top_rrf_score": 0.0325,
  "message": "RAG hybrid search completed"
}
```

**Key Fields:**
| Field | Type | Description |
| :--- | :--- | :--- |
| `request_id` | string | UUID generated by `RequestIDMiddleware` on every request; returned in response header |
| `user_id` | string | Hashed user UUID (never raw Firebase UID or email) |
| `module` | string | Domain module name (e.g., `birth_chart`, `interpretation`) |
| `action` | string | Specific action name (e.g., `rag_search_complete`, `chart_calculated`) |
| `duration_ms` | int | Execution duration for the logged action |

**PII in Logs**: Raw names, birth dates, birth coordinates, and chat message content are NEVER logged. Only UUIDs and computed metrics appear in logs.

## 3. Request ID Middleware

```python
# app/middleware/request_id.py
import uuid
from starlette.middleware.base import BaseHTTPMiddleware
from starlette.requests import Request

class RequestIDMiddleware(BaseHTTPMiddleware):
    async def dispatch(self, request: Request, call_next):
        request_id = str(uuid.uuid4())
        request.state.request_id = request_id
        response = await call_next(request)
        response.headers["X-Request-ID"] = request_id
        return response
```

The `X-Request-ID` header is returned on every response, enabling support teams to find the exact log entry for a user-reported issue by asking the user to copy the request ID from error screens.

## 4. CloudWatch Alarms

| Alarm Name | Metric | Threshold | Action |
| :--- | :--- | :--- | :--- |
| `HighAPIErrorRate` | `5xx_rate` (errors/total requests) | > 2% for 5 minutes | Page on-call via PagerDuty |
| `SlowP95Latency` | `p95_response_time` | > 500 ms for 10 minutes | Alert Slack channel |
| `ChartCalcDLQDepth` | `DLQ message count` (charts queue) | > 0 | Alert Slack + email |
| `HighDBConnections` | RDS `DatabaseConnections` | > 80% of max_connections | Alert Slack |
| `LowRAGConfidence` | Custom metric (Langfuse webhook) | > 5% of queries below 0.65 threshold | Alert AI team Slack |
| `SageSentry5xxSpike` | Sentry error rate | > 10 new events in 5 min | Alert Slack |

## 5. AI Observability with Langfuse

Every call to the LLM provider is traced in Langfuse, capturing:

```python
# app/modules/interpretation/tracing.py
from langfuse import Langfuse
from langfuse.decorators import observe

langfuse = Langfuse(
    public_key=settings.LANGFUSE_PUBLIC_KEY,
    secret_key=settings.LANGFUSE_SECRET_KEY,
    host="https://cloud.langfuse.com",
)

@observe(name="interpretation_pipeline")
async def generate_answer_with_trace(
    question: str,
    chart_id: str,
    prompt_version: str,
) -> AIAnswer:
    """All arguments and return values are traced automatically by Langfuse."""
    # RAG retrieval, prompt assembly, LLM call all happen here
    # Langfuse captures: input tokens, output tokens, duration, model name
    ...
```

**Langfuse Tracks:**
- Input/output token counts per request
- LLM provider latency (TTFB, full completion time)
- Groundedness score (computed from citation match rate)
- Prompt template version used
- Error traces (guardrail blocks, insufficient sources)

## 6. Health Check Endpoint

```python
@router.get("/api/v1/health", include_in_schema=False)
async def health_check(session: AsyncSession = Depends(get_db_session)):
    """
    Comprehensive health check for App Runner liveness probe and CloudWatch Canary.
    Returns 200 only if API + database are both healthy.
    """
    try:
        await session.execute(text("SELECT 1"))
        return {"status": "healthy", "database": "connected", "timestamp": datetime.utcnow().isoformat()}
    except Exception as e:
        return JSONResponse(
            status_code=503,
            content={"status": "unhealthy", "database": "disconnected", "error": str(e)},
        )
```

## 7. Rationale

Structured JSON logging (vs. plain-text logs) is selected because:
- CloudWatch Logs Insights can query fields directly (e.g., `filter module = "interpretation" | stats avg(duration_ms)`).
- Sentry can ingest structured extras for better issue grouping.
- No additional log aggregation tool (e.g., ELK stack) is needed at MVP scale.
